# Event Receiver

Приёмник событий (webhook) с собственной очередью обработки на SQLite.
HTTP-сервис принимает события и атомарно кладёт их в очередь, а отдельный
worker-процесс разбирает очередь с повторными попытками и восстановлением
после сбоев.

## Стек

- Python 3.11+ (проверено на 3.12)
- Flask — HTTP API
- SQLite (модуль `sqlite3` из стандартной библиотеки) — хранилище и очередь
- pytest — тесты

Готовые движки очередей (Celery, RQ, Huey) не используются.

## Требования к окружению

- Python 3.11 или новее
- SQLite с поддержкой JSON1 (входит в стандартную сборку Python; используется
  `CHECK (json_valid(payload))`)
- Файловая система, на которой работает SQLite WAL (локальный диск; не NFS)

## Установка

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

## Запуск

Flask-приложение (по умолчанию порт 5000):

```bash
flask --app app run
```

Worker (в отдельном терминале; запускать можно несколько экземпляров):

```bash
python -m app.worker
```

Остановка worker — `Ctrl+C` (SIGINT) или SIGTERM: текущая задача дорабатывается,
после этого процесс завершается с кодом 0.

База создаётся автоматически при старте приложения и worker.

### Конфигурация (переменные окружения)

| Переменная                    | По умолчанию | Назначение                                           |
|-------------------------------|--------------|------------------------------------------------------|
| `EVENTS_DB_PATH`              | `events.db`  | Путь к файлу SQLite (общий для API и worker)         |
| `MAX_ATTEMPTS`                | `3`          | Максимум попыток обработки задачи                    |
| `RETRY_BASE_DELAY_SECONDS`    | `1.0`        | Базовая задержка экспоненциального backoff           |
| `LOCK_TIMEOUT_SECONDS`        | `30.0`       | Через сколько секунд блокировка задачи считается зависшей |
| `WORKER_POLL_INTERVAL_SECONDS`| `1.0`        | Пауза worker при пустой очереди                      |
| `SQLITE_BUSY_TIMEOUT_MS`      | `5000`       | Сколько SQLite ждёт освобождения блокировки записи   |
| `MAX_CONTENT_LENGTH`          | `1048576`    | Максимальный размер тела запроса (байт)              |
| `LOG_LEVEL`                   | `INFO`       | Уровень логирования                                  |

`API` и worker должны использовать один и тот же `EVENTS_DB_PATH`.

## API

### `POST /webhook`

```bash
curl -i -X POST http://localhost:5000/webhook \
  -H 'Content-Type: application/json' \
  -d '{"event_id": "abc-123", "type": "payment_succeeded",
       "payload": {"amount": 1000, "currency": "USD"}}'
```

Ответ `200`:

```json
{"event_id": "abc-123", "message": "Event accepted and queued for processing",
 "status": "accepted", "task_id": 1}
```

Повторная отправка того же `event_id` — тоже `200`, но новых записей нет:

```json
{"event_id": "abc-123", "message": "Event already exists",
 "status": "duplicate", "task_id": 1}
```

Ошибки валидации (`400`, битый JSON, не-объект, пустые/нестроковые `event_id`
и `type`, `payload` не объект, NaN/Infinity в payload, слишком длинные поля):

```json
{"error": "Field 'payload' is required and must be a JSON object"}
```

Другие коды: `413` (тело больше `MAX_CONTENT_LENGTH`), `503` + `Retry-After`
(SQLite недоступна дольше `SQLITE_BUSY_TIMEOUT_MS`).
Все ошибки возвращаются в JSON.

### `GET /stats`

```bash
curl http://localhost:5000/stats
```

```json
{
  "events": {"payment_failed": 3, "payment_succeeded": 10},
  "tasks": {"failed": 1, "pending": 2, "skipped": 0, "success": 8}
}
```

Все четыре статуса задач присутствуют всегда (с нулями). Оба блока считаются
одним SQL-запросом, поэтому согласованы между собой.

### Имитация сбоев

Обработка детерминированно «падает», если в `payload` передать
`"simulate_failures": N` — первые `N` попыток завершатся ошибкой:

```bash
# 2 ошибки подряд (1 с, затем 2 с задержки), на 3-й попытке — успех
curl -X POST localhost:5000/webhook -H 'Content-Type: application/json' \
  -d '{"event_id":"flaky-1","type":"payment_succeeded","payload":{"simulate_failures":2}}'

# 3 ошибки — задача станет failed
curl -X POST localhost:5000/webhook -H 'Content-Type: application/json' \
  -d '{"event_id":"bad-1","type":"payment_failed","payload":{"simulate_failures":3}}'
```

Типы событий: `payment_succeeded`, `payment_failed` обрабатываются;
любой другой тип получает статус `skipped`.

## Тесты

```bash
pytest
```

Тесты используют временную SQLite-базу (`tmp_path`), не зависят друг от друга и
не содержат `sleep` для проверки задержек: время передаётся в очередь параметром,
в тестах используются управляемые часы (`FakeClock`).

## Структура проекта

```
app/
├── __init__.py      # create_app(): фабрика Flask-приложения
├── config.py        # Settings, RetryPolicy, чтение переменных окружения
├── database.py      # подключения, транзакции BEGIN IMMEDIATE, схема
├── routes.py        # POST /webhook, GET /stats, валидация, обработчики ошибок
├── task_queue.py    # очередь: enqueue / claim / complete / fail / stats
├── processor.py     # бизнес-логика обработки событий (не знает про очередь)
├── timeutils.py     # единый формат времени (UTC)
└── worker.py        # python -m app.worker
tests/               # webhook, worker/очередь, stats, processor, database
```

Модуль назван `task_queue.py`, а не `queue.py`, чтобы не затенять модуль
стандартной библиотеки `queue`.

## Структура базы данных

**events**

| Поле         | Тип     | Описание                                             |
|--------------|---------|------------------------------------------------------|
| `id`         | INTEGER | PK                                                   |
| `event_id`   | TEXT    | внешний идентификатор, `UNIQUE`, непустой            |
| `type`       | TEXT    | тип события, непустой, индекс `idx_events_type`      |
| `payload`    | TEXT    | JSON-объект (`CHECK json_valid AND json_type = 'object'`) |
| `created_at` | TEXT    | UTC, формат `YYYY-MM-DDTHH:MM:SS.ffffffZ`            |

**tasks**

| Поле            | Тип     | Описание                                           |
|-----------------|---------|----------------------------------------------------|
| `id`            | INTEGER | PK, определяет порядок FIFO                        |
| `event_id`      | INTEGER | FK → `events.id`, `UNIQUE` (ровно одна задача на событие) |
| `status`        | TEXT    | `pending` / `success` / `failed` / `skipped` (`CHECK`) |
| `attempts`      | INTEGER | число начатых попыток (растёт в момент взятия задачи) |
| `next_retry_at` | TEXT    | не раньше этого времени задачу можно брать         |
| `last_error`    | TEXT    | последняя ошибка (сохраняется и после успешного ретрая) |
| `locked_at`     | TEXT    | когда задача взята в работу                        |
| `locked_by`     | TEXT    | идентификатор worker (`CHECK`: оба поля NULL или оба заданы) |
| `created_at`, `updated_at` | TEXT | время создания / последнего изменения  |

Индексы: частичный `idx_tasks_pending (next_retry_at, id) WHERE status='pending'`
для выборки готовых задач и `idx_tasks_status` для `/stats`.
Для каждого соединения явно выполняется `PRAGMA foreign_keys = ON`; режим
журнала — WAL (читатели не блокируются писателем).

## Как работает очередь

Очередь — это таблица `tasks`. Состояние «в работе» отдельным статусом не
хранится: задача остаётся `pending`, а поля `locked_by` / `locked_at` показывают,
что её кто-то обрабатывает.

1. **Постановка.** `enqueue_event` в одной транзакции делает
   `INSERT INTO events ... ON CONFLICT (event_id) DO NOTHING`. Если строка не
   вставилась — событие уже есть, возвращается его задача (`created=False`).
   Иначе в той же транзакции создаётся задача `pending`. Событие и задача либо
   появляются вместе, либо не появляются вовсе. Защиту от гонок обеспечивает
   `UNIQUE`-ограничение (то же, что ловил бы `IntegrityError`, но без
   исключения), а `BEGIN IMMEDIATE` дополнительно сериализует запись.
2. **Получение.** `claim_next_task` в транзакции `BEGIN IMMEDIATE`
   выбирает самую раннюю (`ORDER BY id`) задачу, у которой
   `status='pending'`, `next_retry_at <= now` и либо нет блокировки, либо она
   истекла; затем ставит `locked_by`/`locked_at` и увеличивает `attempts`.
   Write-lock берётся до чтения, поэтому два worker не могут забрать одну задачу;
   проигравший ждёт до `SQLITE_BUSY_TIMEOUT_MS`.
3. **Завершение.** `UPDATE ... WHERE id=? AND locked_by=? AND status='pending'`.
   Результат применяется, только если worker всё ещё владелец блокировки (см.
   ниже), иначе он отбрасывается и логируется.

Гарантия — *at-least-once*: при сбое между обработкой и записью результата
событие может быть обработано повторно, поэтому реальные обработчики должны быть
идемпотентными.

## Повторные попытки

- Максимум `MAX_ATTEMPTS = 3` попытки.
- После ошибки попытки `n` задача остаётся `pending` и получает
  `next_retry_at = now + base_delay * 2^(n-1)`:

| Результат попытки | Действие                                  |
|-------------------|-------------------------------------------|
| 1-я ошибка        | повтор через 1 с                          |
| 2-я ошибка        | повтор через 2 с                          |
| 3-я ошибка        | статус `failed`, задача больше не выбирается |

- Текст ошибки (`ИмяИсключения: сообщение`) пишется в `last_error`.
- Любое исключение обработчика перехватывается: worker не падает из-за одной
  задачи.
- Неизвестный тип события — не ошибка и не ретраится: статус `skipped`.

## Зависшие задачи и защита от вечного `pending`

**Проблема:** worker взял задачу и умер (kill -9, перезапуск, OOM), блокировка
осталась навсегда.

**Решение:**

1. Блокировка имеет срок жизни: задача с `locked_at <= now - LOCK_TIMEOUT_SECONDS`
   снова доступна для `claim_next_task` (любым worker, в том числе после
   перезапуска).
2. `attempts` увеличивается в момент *взятия* задачи, а не после обработки.
   Значит, worker, который падает на каждой попытке, тоже «расходует»
   попытки.
3. Если срок блокировки истёк, а попытки исчерпаны (`attempts >= MAX_ATTEMPTS`),
   задача переводится в `failed` с `last_error = "Lock expired ..."`. Это
   делается в той же транзакции, что и выбор следующей задачи.
4. Worker, обработка которого затянулась дольше таймаута, не может перезаписать
   чужой результат: завершение проверяет `locked_by`.

Итог: у каждой задачи конечное число попыток, а каждая попытка либо
завершается записью результата, либо через `LOCK_TIMEOUT_SECONDS` становится
доступна снова. Бесконечный `pending` возможен только пока **не запущен ни один
worker** — это ожидаемое поведение (задачи ждут обработки), а не зависание.

При перезапуске worker ничего не теряется: всё состояние хранится в SQLite, а не в памяти процесса.

`LOCK_TIMEOUT_SECONDS` должен быть заметно больше времени обработки самой долгой
задачи, иначе задачу возьмёт второй worker, пока первый ещё работает.

## Архитектурные решения

- **Плоская структура, 8 модулей.** Нет репозиториев, фабрик и иерархий классов:
  SQL лежит рядом с логикой очереди в `task_queue.py`. Классов два
  (`Worker`, датаклассы) — только там, где есть состояние.
- **Очередь отделена от бизнес-логики.** `processor.py` ничего не знает о БД и
  статусах; `worker.py` связывает их: `UnknownEventTypeError` → `skipped`,
  любое другое исключение → ретрай.
- **Время передаётся параметром** (`now`), а не берётся внутри функций очереди.
  Благодаря этому задержки и истечение блокировок тестируются без `sleep` и
  `mock`.
- **Один источник подключений.** `database.connect()` — контекстный менеджер:
  PRAGMA, `row_factory`, гарантированное закрытие. Глобальных соединений нет.
- **Одна таблица очереди, статус `pending` + lock-поля.** Не нужен 5-й статус
  `processing`, статусы совпадают с требованиями, а восстановление зависших
  задач делается одним условием по `locked_at`.
- **Время хранится строкой фиксированной ширины в UTC**, поэтому сравнение строк
  в SQL эквивалентно сравнению времени и работает с индексом.
- **Конфигурация** — неизменяемые датаклассы; значения по умолчанию — именованные
  константы, ошибки конфигурации сообщаются при старте.

## Известные ограничения

- SQLite допускает одного писателя одновременно: решение рассчитано на единицы
  worker-процессов на одной машине, а не на высокую пропускную способность.
  WAL не работает на сетевых файловых системах.
- Доставка at-least-once (см. выше); обработчики должны быть идемпотентными.
- Нет таймаута на выполнение одной задачи: «зависший» обработчик (бесконечный
  цикл) блокирует свой worker, хотя задачу после истечения блокировки заберёт другой.
- Нет ручного перезапуска `failed`-задач, очистки старых записей и метрик.
- Повторный `event_id` с другим телом игнорируется (сравнение payload не
  делается): первое событие считается каноничным.
- `simulate_failures` доступен любому отправителю webhook: это тестовый механизм,
  в production его нужно отключить.
- Нет авторизации, подписи webhook и ограничения частоты запросов (по условию
  задания).
- Worker опрашивает очередь по таймеру; push-уведомлений нет, поэтому
  задержка старта обработки — до `WORKER_POLL_INTERVAL_SECONDS`.
